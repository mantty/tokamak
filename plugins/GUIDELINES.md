# Creating a Tokamak plugin

A plugin is one npm package. Its native SDK receives a `TokamakContext`; Tokamak
generates the page client and worker service binding from its exported methods.
The app uses the same project, dependencies and build commands.

## Start a package

```sh
tok plugin page-tools
# Or start with a small native implementation:
tok plugin device-tools --native apple
tok plugin device-tools --native android
```

The default scaffold composes `ctx.webview` in TypeScript. Native scaffolds add
one small Swift or Kotlin endpoint that emits an event, declared in `/events`.
Each has a browser implementation in `web/`. None requires Rust, a custom
protocol, or a separately maintained frontend router. The directory must be new.

Install dependencies in the package and run `npm run check`. Add it to your
app with `npm install ../page-tools`, a pnpm workspace dependency, or Yarn's
equivalent. Run the app's usual `tok dev` command. Vite reloads TypeScript;
native changes require rebuilding the app.

## Declare the callable API once

```ts
import type { TokamakContext } from "@tokamakdev/plugin";

export function pageTools(ctx: TokamakContext) {
  return {
    getCurrentPage(): Promise<string | null> {
      return ctx.webview.getCurrentPage();
    },
  };
}
```

Reference the factory in `tokamak-plugin.json`:

```json
{
  "schemaVersion": 2,
  "id": "page-tools",
  "api": { "module": "src/index.ts", "export": "pageTools" }
}
```

The app's Tokamak worker calls `pageTools(ctx).getCurrentPage()`. Page code
imports the default generated client from `tokamak-plugin-page-tools/client`.
The main worker uses the optional generated `env.TOKAMAK_PAGE_TOOLS` binding.
Editor declarations are generated by the existing Vite integration.

Describe where operations run in the manifest's `operations`. An operation runs
on every platform in `platforms` unless it names its own, each with a minimum
OS version or `true` for the app's minimum; `foreground` lists the platforms
where it may need the app on screen to show UI:

```json
"operations": {
  "requestPermission": { "foreground": ["ios", "android"] },
  "onVisit": { "platforms": { "ios": true, "macos": true } }
}
```

Generated editor documentation lists each operation's platforms, versions,
browser implementation and foreground needs. `capabilities` on the native SDK
(a `Plugin` getter, or `capabilitiesOf(ctx, id)` for an object factory) and on
the generated client reports whether each operation is implemented where the app
runs: the native platform, or the browser implementation on the web. It does not
report permission. `ctx.platform` names the native platform.

Only expose data, errors and byte `ReadableStream`s in the callable API. Public
calls return promises at the caller. Functions, arbitrary class instances and
remote objects cannot cross this boundary; invalid signatures fail generation.
Keep low-level native objects inside the Tokamak worker.

## Bind platform APIs

A plugin's `/apple` and `/android` exports are its platforms' own APIs,
generated from the SDKs' API descriptions. List the modules to bind:

```json
"bindings": {
  "apple": ["CoreLocation", "_LocationEssentials"],
  "android": ["android.location", "android.content.Context"]
}
```

An Apple entry names a Swift module, including one a framework re-exports
through its headers, such as `_LocationEssentials` for `CLLocation`. An Android
entry names a package or a class. Run `tok bindings` in the package, with Xcode
and the Android SDK (`ANDROID_HOME`) installed. It writes `apple/bindings.ts`,
`apple/Bindings.swift`, `android/bindings.ts` and `android/Bindings.kt`, and
lists each symbol it leaves out with the reason. Commit them and export the
modules as `"./apple": "./apple/bindings.ts"` and `"./android":
"./android/bindings.ts"`. App builds compile and register the generated native
source. A plugin needs no native code of its own to bind, and one that imports
another package's bindings depends on that package, which the app then
includes.

The bindings keep the platform's names, types and objects:

- Classes are classes. Every member returns a promise; static members and
  initializers take the invocation's `ctx` first. A property `x` is `x()` and
  `setX(value)`. Nested types join their names with `$`, as the JVM does:
  `Notification$Builder`.
- Apple members take their Objective-C selector's name:
  `locationManager:didUpdateLocations:` is `locationManagerDidUpdateLocations`.
  Swift-only members and `async` variants take their Swift name and labels.
- Structs are plain objects, enums their case names, option sets arrays of
  names, `Date` a `Date`, and `Data` or `byte[]` a `Uint8Array`.
- Android overloads are TypeScript overloads, chosen by the arguments' types.
  Compile-time constants are `static readonly` fields.
- An Apple `async` function returns a promise, and takes an optional last
  `{ signal }` whose abort cancels its task. One returning an `AsyncSequence`
  returns a `ReadableStream`.
- `Protocol.implement(ctx, handlers)` creates a native delegate, listener or
  abstract-class callback that calls `handlers`. A method without a handler
  keeps its platform default.
- Platform errors reject with `OperationError`, whose `cause` is
  `{ domain, code }` from Apple and `{ exception }` from Android. A member the
  running OS lacks rejects with `NotSupportedError`; editor docs list each
  symbol's platforms and versions.

Calls run on the main thread. Objects belong to the invocation that received
them: `release(object)` lets go of one early.
`new Class(referenceOf(object))` views an object as another class, and
`referenceOf(object)` passes it to a plugin's native endpoint.
`release`, `referenceOf`, `applicationContext(ctx)`, `foregroundActivity(ctx)`
and `presenter(ctx)`, which give the app's own objects, come from
`@tokamakdev/plugin/bindings`.

Compose a cross-platform API from the bindings where they suffice, as the
location plugin's `getCurrentPosition` composes `CLLocationManager` and
`LocationManager`. What the descriptions cannot express needs native code:
closures other than `async` completions, C pointers, callbacks that return a
value, and registrations that outlive an invocation.

## Native code and codecs

Extend `Plugin` for native endpoints. Its protected `call` encodes ordinary
values; `callBytes` carries raw bytes; `stream` returns encoded values consumed
with `decodeValues` from `@tokamakdev/plugin/streams`.

Both calls take `{ signal, body }`. Aborting `signal` cancels the native work.
A `body` is a `ReadableStream<Uint8Array>` that the native endpoint reads one
chunk at a time, through Swift `call(method:arguments:body:reply:)` or Kotlin
`call(method, arguments, body, reply)`: each `body.read` pulls the next chunk,
nil after the last, so the Worker sends no faster than the plugin reads. A
native source the reader drives, such as a file, is a call per chunk from a
`ReadableStream`'s `pull`.

`stream(method, value, overflow)` buffers up to 1 MiB for a slow reader. Pass
`"dropOldest"` for samples where only recent values matter, such as sensor
readings; the default `"error"` ends the stream with `QuotaExceededError`.

Swift `TokamakPlugin.call` and Kotlin `TokamakPlugin.call` receive decoded JSON
and return ordinary values through their reply callback. A reply of Swift `Data`
or Kotlin `ByteArray` is sent as raw bytes, which TypeScript reads with
`callBytes`. Override `callBytes` or `subscribeBytes` when your capability needs
its own binary argument format. Routing, failure and completion travel
separately from payload bytes.

Large native data stays native. A subscription retains an object with
`host.resources.retain(object, reply:)` and returns the release it gives back.
TypeScript acquires it with the protected `resource(method)`, which resolves to
a `NativeReference` owned by the invocation. Pass it to another plugin with
`reference(value)` inside the call's arguments; that plugin's native code finds
the same object with `host.resources.get(id, as:)` on Apple or
`host.resources.get(id, Type::class.java)` on Android. `close()` or the end of
the invocation releases it, and so does garbage collection where the Worker
has `FinalizationRegistry` (Workers from compatibility date 2025-05-05).
`bytes()` copies the current contents of a retained `Data` or `ByteArray` into
JavaScript.

```ts
class Camera extends Plugin {
  capture(): Promise<NativeReference> { return this.resource("capture"); }
}
class Encoder extends Plugin {
  encode(frame: NativeReference): Promise<number> {
    return this.call("encode", { frame: this.reference(frame) });
  }
}
```

Native plugins select a serial executor per operation with `executor(for:)`
on Apple or `executor(method)` on Android. The default is the UI thread; use a
plugin-owned queue for work that does not need it. Cancellation uses that same
executor. Replies can arrive on any thread and go directly to the runtime.

Return cancellation for pending native work. Subscription cancellation releases
its resources when the stream ends or the invocation is torn down. App-owned
background registrations need stable IDs and documented restoration rules;
they must survive the short invocation that configured them.

## Native screens and sessions

A plugin shows a native screen from Swift `host.presenter()`, a view controller
on iOS and the window on macOS, or Kotlin `host.requireForegroundActivity()`, on
the main thread. Both reject with `NeedsUIError` while the app cannot show UI.
The plugin presents and dismisses its screen; the page is unaffected.

An operation that leaves a screen or a hardware session open after its call
completes returns a session ID and offers an explicit close or stop operation.
The session belongs to the app, so a later invocation ends it by that ID. A
session that belongs to one invocation is a `NativeReference` or a stream
instead, which closing or the invocation's end releases.

The manifest's `platforms` entries name the native class and source files.
Support one platform if that is what the capability needs. Add permissions and
other packaging metadata through the existing platform build hooks.

## Events and browser implementations

Declare each event's data, and any reply, in your types module, then export
typed registration functions from `/events`:

```ts
declare global {
  namespace Tokamak {
    interface Events { "sensor.reading": { value: number } }
    interface EventReplies { "sensor.reading": { accepted: boolean } }
  }
}

export const onReading = defineEvent("sensor.reading");
```

The declarations also type the app's `event(event)` handler, whose
`TokamakEvent` is a union of every declared event. Event data and replies travel
as JSON; pass `defineEvent` a codec to carry them as other bytes.

Import and register listeners from `src/tokamak.ts` or its imports. A listener
receives `(event, env, ctx)`, may call another plugin with `ctx`, and may return
a typed response. Native code emits the event with `host.emit` (JSON) or
`host.emitBytes` (bytes) and applies the reply using the platform callback's
deadline; an empty reply means no listener replied. Synchronous OS callbacks use
native configuration; they cannot wait for JavaScript.

A browser implementation is optional. Put it in a separate module and reference
its exported object with `web: { module, export }` in the manifest. Each method
implements the corresponding generated frontend signature. Omitted methods
reject with `NotSupportedError` on the web. Native SDKs never import this module.

## Publish

Inspect `npm pack --dry-run`, install the resulting tarball in an app, and check
both `tok dev` and a packaged build. Then use normal `npm publish` tooling,
changing the package name to your own npm scope if desired. Keep the plugin ID
stable: native events, generated bindings and settings use it.
